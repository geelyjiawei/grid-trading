## 用户的长期要求

- 网格订单必须由确定性计划产生，不能随机补单、超额开单或通过保护单掩盖台账错误。
- 固定每格数量模式下，每格数量应一致；只能按交易所 `tickSize`、`stepSize`、最小数量和最小名义金额做可解释的规范化。
- 成交后应尽快提交对应反向网格单，WebSocket 是主路径，REST 仅用于恢复和核对。
- 交易所订单、成交和仓位是权威事实；本地数据库是可重建账本，不能反过来覆盖交易所事实。
- 下单和补单必须使用幂等客户端订单 ID，避免重试导致重复订单。
- 成交记账失败不能直接撤销其他正常网格单；应冻结有歧义的状态并做权威核对。
- 停止策略必须快速撤销本策略订单，但不得主动平掉用户已有仓位或误撤手工订单。
- 手工订单与策略订单必须依靠客户端订单 ID、策略运行 ID和订单归属字段区分。
- 所有代码更新都要经过测试、提交并推送 GitHub，方便回滚。
- GitHub 中不得包含 `.env`、API 密钥、钱包私钥、登录密码或动态验证码种子。

## 最近完成的 Aster 修复

提交 `dcaf479` 优化了 Aster 首次成交后的补单路径：

- Aster 下单请求使用官方 `newOrderRespType=RESULT`。
- 校验交易所返回的订单 ID、客户端订单 ID、方向、价格、数量、生命周期、已成交数量和更新时间。
- 把已接受的新订单绑定到 `FuturesExecutionCache`，使首次成交可以由官方 WebSocket 的 `NEW + TRADE` 事件直接组成权威成交快照。
- 正常路径不再为了首次成交额外请求 `/order` 和 `/userTrades`。
- Aster 只返回最小 ACK 时仍接受权威订单 ID，并安全回退到 REST，不得把成功下单误判成失败后重复下单。
- 增加补单确认延迟指标：`accepted_submissions`、`event_to_submit_ms`、`exchange_to_observed_ms`、`exchange_to_submit_ms`。
- 本地观察成交到补单确认超过 1000ms 时记录 SLO 告警。

- `rust-backend/src/lib.rs`

## 继续工作时的检查顺序

1. 先执行 `git status --short --branch`，不得覆盖用户未提交修改。
2. 核对本地 HEAD、远端分支和生产镜像是否一致。
3. 读取生产健康状态、容器重启次数和相关策略日志；默认只读，不操作真实订单。
4. 对速度问题按“交易所成交时间 -> WebSocket 到达 -> 本地处理 -> 提交请求 -> 交易所确认”分段测量，不能只看网页刷新时间。
5. 修复必须先有能复现根因的失败测试，再做最小改动，并跑专项测试、完整 Rust 测试和 Clippy。
6. 部署前备份生产镜像与策略数据库，部署后检查健康状态和日志。
7. 每次代码变更提交并推送 GitHub；提交前运行秘密扫描或至少检查被跟踪文件中没有凭据。
